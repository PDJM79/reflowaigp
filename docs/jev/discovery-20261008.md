## 3. Top 3

**G1: match a training record to a training type.** This is the cleanest slot in the repo. It is a pure choice from a short list the practice owns. A human does it today, one record at a time, and can override with the same control. Today a wrong answer changes only a badge (`type_id` is read nowhere else). It touches no personal data if the input is limited to the course name. *Input state:* `{ course_name: "Fire Safety Awareness L1 (e-learning)", provider?: string, options: [{id, name, renewal_frequency}] }`, with the employee left out. *Typed question:* "Which of these training types is this record?" Return a choice from the option ids plus "none", with a probability. Only show a suggestion above a threshold and never write without a click. *Wrong answer:* a mistyped record. That is visible and reversible now. It would cost more later if `type_id` started feeding training compliance (see section 5).

**G5: complaint escalation-risk flag.** Today a large generative call returns `risk_areas` with a `risk_level` hidden inside free JSON. The code needs three layers of parse repair and falls back to nothing (complaintAnalysis.ts:218-264). A per-complaint boolean ("could this escalate to the Public Services Ombudsman for Wales or HIW?") with a probability would be steadier and could be audited, and the prose summary could stay on Mistral. *Input state:* category, severity, channel, ack and final SLA status (already computed), and the redacted description excerpt (120 characters, initials only). *Typed question:* boolean P(escalation risk). *Wrong answer:* a missed flag means a manager does not prioritise a complaint that later escalates. This is special-category data, so it is blocked until EU residency is confirmed in writing.

**G3: suggested complaint category and severity at logging.** The form defaults to `other`/`low` (LogComplaintDialog.tsx:21-22), so careless entries land in the least useful bucket. That weakens the theme analysis and SLA views downstream. A suggestion pre-selected from the description, which staff confirm, is a real data-quality gain. *Input state:* the description text and channel. *Typed question:* choice of 6 categories, choice of 3 severities. *Wrong answer:* a mis-bucketed complaint. A human sees the suggestion before saving, but people accept pre-filled values, so severity needs a high probability bar or should not be pre-filled at all. Special category again.

## 4. Pilot proposal

**None now, because there is no volume.** GP prod holds 0 training records, 0 complaints, 0 incidents, 0 baseline documents and 0 `ai_usage` rows (counted 8 Oct 2026). A pilot would decide nothing, and you cannot build a real test set from empty tables.

When to revisit, and what to run: once a practice has typed even 30 to 50 training records by hand, run **G1** as a shadow decision through the Phase 1 decision helper. Use a synthetic test set first. Feature flag off by default. Show the suggestion in the existing dropdown with no auto-write, and log the question id, input hash, chosen id, probability, model and latency into the existing `ai_usage` pattern (`server/services/mistral.ts` `logUsage`). G1 needs no personal data, so it is the only candidate here that could reasonably run before EU residency for Jev is answered. Even so, sending course names to a new processor needs Phil's sign-off. The same helper running on Mistral EU through the P(true) adapter is a valid fallback design if Jev is ruled out.

## 6. Escalations (Phil decisions)

1. **New vendor and secret.** Using Jev means a Vercel account plus `AI_GATEWAY_API_KEY` (or OIDC) on Render and possibly in Supabase secrets, and a new DPA or sub-processor entry for a UK GP compliance platform. Not started.
2. **The CI guard here does not block Jev, which is the opposite of what the brief assumes.** GP has no `ai-provider-guards.yml`. Its guard is `scripts/checkAiProvider.mjs` (run in `.github/workflows/ci.yml:24`), and it is a **deny-list**: retired provider hosts, keys and model ids, plus non-EU Mistral hosts (lines 31-43). A call to `ai-gateway.vercel.sh` or the `typesafe-ai/jev` model id would **pass CI unnoticed**. Any Phase 1 change should turn the guard into an explicit allow-list in the same change, otherwise "Mistral only, EU only" stops being true without any warning.
3. **Spend.** Negligible at current volume (zero). No budget needed until there is usage.
4. **Special-category data.** G3, G4, G5 and G11 involve patient data. They should not be piloted on a non-EU-confirmed processor under any circumstances. They need written residency and a DPIA update first.
5. **G2 is a product question before it is a Jev question.** `process-baseline-documents` classifies by filename only, its output is unused, and it runs on Lovable. Either finish it (real document extraction on Mistral EU, then close the guard exception) or remove it. Jev adds nothing until that is decided.
